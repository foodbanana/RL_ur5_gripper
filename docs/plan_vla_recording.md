# 2단계 계획: 선생 정책으로 VLA 시범 데이터 만들기 (검토용 초안)

목표: 특권 정보 선생 정책(현재 `try20b`, 또는 21a/21b 중 더 나은 것)으로 시뮬레이터에서 드론 파지 에피소드를 돌리고,
**기존 실물 데이터셋과 같은 LeRobot v2.1 형식**으로 저장한다. 이 데이터로 VLA(π0.5 등)를 학습하고, 나중에는 카메라 학생 정책
증류에도 쓴다.

원칙
- 기존 레포(`~/data_collection_ur5_gripper`)는 읽기만 한다. 필요한 값은 이 레포에 복사한다.
- 데이터 스키마·카메라·주기는 **기존 실물 데이터와 같게** 한다(섞어 쓰거나 비교할 수 있게).
- **카메라는 1대만 쓴다: 로봇 팔 카메라 마운트의 손목 카메라(D435i).** Stewart·Husky 플랫폼에서는 외부(third view) 카메라를
  둘 곳이 없어서 실물에서도 손목 카메라 1대만 썼다. 고정 테이블·Stewart·Husky 데이터가 같은 입력을 갖도록 모두 1대로 맞춘다.
- 학습 환경(`DroneGraspRl-Grasp-UR5`)은 바꾸지 않는다. 녹화용 설정은 별도 태스크/설정으로 둔다.
- 다른 PC에서 재현 가능하게(경로 하드코딩 없음, 에셋은 LFS, 의존성은 `uv.lock`).

## 1. 기준이 되는 기존 데이터 형식 (확인 완료)

| 키 | 정의 | sim에서 만드는 방법 |
|---|---|---|
| 형식 / fps | LeRobot v2.1, **25 fps**, lerobot 0.3.3, 영상 av1 / yuv420p | 30 Hz로 돌리고 25 Hz 격자로 다시 샘플링 (4장) |
| `observation.state[0:6]` | 측정 관절각 [rad] | `robot.data.joint_pos` (팔 6) |
| `observation.state[6]` | 그리퍼 present/1150 (0 = 열림, 0~1 연속) | `rh_r1_joint 위치 / 상한` (기존 sim과 같은 선형 매핑) |
| `action[0:6]` | 절대 관절 목표 [rad] (`/joint_command`) | 팔 행동 term의 관절 목표 (필터·감속 적용 후 실제로 보낸 값) |
| `action[6]` | 그리퍼 goal/1150 ∈ {0, 1} | 그리퍼 래치 상태 (닫기 = 1) |
| `observation.base_imu` | (6,) 고정 베이스는 상수 [0,0,0,0,0,9.81] | 같은 상수 (Stewart·Husky에서는 베이스 IMU 값) |
| `observation.images.wrist` | 640×480 RGB, D435i | 손목 카메라 (2장). **이미지 키는 이것 하나** |
| 메타 | seed, 드론 목표/위치(world·base), hover 프리셋, 모터 정지 시각·프레임 등 | 같은 항목 + 판정 결과, 선생 체크포인트 이름 |

## 2. 카메라: 손목 카메라 1대 (기존 레포 값을 그대로 복사)

| 항목 | 손목 (D435i, 로봇 팔 카메라 마운트) |
|---|---|
| 위치 | URDF의 `wrist_camera_color_optical_frame` (로봇 USD에 이미 있음), 10° 기울어진 마운트 |
| 내부 파라미터 | fx 618.55, fy 618.96, cx 332.28, cy 239.38 (가로 54.7°, 세로 42.4°) |
| 렌더 | 640×480 RGB, 왜곡 0, clipping 0.01~10 m |
| 모양 | 로봇 USD에 포함 |

- 외부(third view, D456) 카메라는 쓰지 않는다. 기존 레포에 설정이 있지만 Stewart·Husky에서는 설치할 수 없었다.
- 카메라가 1대라 드론과의 거리(깊이)는 손목 영상 하나로 추정해야 한다. 잡기 직전에는 드론이 화면 대부분을 차지하므로
  가까운 거리는 잘 보이지만, 먼 출발 위치에서는 드론이 작게 보인다. 필요하면 depth 영상 저장도 검토한다(D435i는 depth도 있음).
- Isaac Lab `TiledCameraCfg`(또는 `CameraCfg`)를 손목 링크 아래, **녹화용 장면에만** 추가한다. 학습 장면은 카메라 없이 그대로 빠르게 유지한다.
- USD 카메라 변환(aperture, 가로 오프셋 부호, 픽셀 중심 +0.5)은 기존 레포 방식 그대로 따르고, **투영 오차 검사**로 확인한다
  (기존 검사: TCP가 손목 영상에서 (332, 446) 근처, 최대 오차 0.22 px).
- 렌더러: PhysX 경로이므로 Isaac RTX(Kit). `renderer_cfg`를 명시한다.

## 3. 녹화 스크립트 `scripts/record_demos.py` (새로 만듦)

1. 선생 체크포인트를 불러와 env N개(예: 16~32개, VRAM 보고 결정)로 돌린다.
2. 매 정책 스텝(30 Hz)마다 state, action, 손목 카메라 영상, 판정 단계를 env별 버퍼에 쌓는다.
3. 에피소드가 끝나면:
   - **성공(HELD)한 에피소드만** 저장 (실패는 개수만 기록). 기존 실물 데이터도 성공만 저장했다.
   - 성공 뒤 약 1 s 더 녹화해서 "잡고 버티는 끝 장면"을 남긴다(실물 데이터의 마무리와 비슷하게).
4. 중간 파일(에피소드별 npz + 프레임)로 먼저 쓰고, 5장의 변환기가 LeRobot v2.1로 만든다.
   녹화와 변환을 나누는 이유: lerobot 패키지는 torch 버전 등을 고정해서 Isaac Lab 환경과 충돌할 수 있다.

녹화 조건(초안)
- 시작 위치: 원래 25곳 (실물 데이터와 같은 목표). 커리큘럼(가까운 시작)은 끔.
- hover: static / small / mid / big를 섞음 (비율은 검토 사항).
- 물리 랜덤화: 학습 때와 같이 켬 (마찰, 질량, 게인, 지연, 외란).
- 행동에는 잡음을 넣지 않음 (선생의 평균 행동 = 결정적).

## 4. 25 fps vs 30 Hz

| 방법 | 내용 | 장단점 |
|---|---|---|
| **A. 30 Hz로 돌리고 25 Hz로 다시 샘플링 (추천)** | 기존 1단계 변환기와 같은 규칙: 25 Hz 격자마다 **직전 최신 프레임**(ZOH) | 실물 데이터가 만들어진 방식(30 Hz 카메라 → 25 Hz 격자)과 같음. 정책·물리를 바꿀 필요 없음 |
| B. 정책을 25 Hz로 다시 학습 | 물리 1/100 s × decimation 4 | 선생을 다시 학습해야 함. 게인·제어 특성이 바뀜 |
| C. 30 fps로 저장 | 그대로 | 기존 데이터와 fps가 달라 섞을 수 없음 |

- 실물에서는 영상이 state보다 0~25 ms(중앙 16.7 ms) 늦었다. 필요하면 영상을 한 스텝 전 것으로 붙이는 옵션을 둔다.

<br>

## 5. LeRobot v2.1 변환기 `tools/lerobot_export/`

- 기존 레포의 `lerobot_v21_common.py` / `lerobot_stage2_build_dataset_v21.py` 방식을 복사해 고친다(features, 검사 규칙 동일).
- **별도 uv 프로젝트**(자체 `pyproject.toml` + `uv.lock`, `lerobot==0.3.3`)로 둬서 Isaac Lab `.venv`와 섞지 않는다.
- 결과 검사: 기존 `inspect_dataset_v21.py`와 같은 항목(키, shape, fps, 프레임 수, 영상 길이, state·action 범위, 그리퍼 0/1 이진).
- 출력은 `datasets/`(git 무시). 큰 데이터는 레포에 넣지 않는다.

## 6. 시각 랜덤화 (VLA가 실물 영상에 일반화하도록)

| 대상 | 범위 (초안) | 비고 |
|---|---|---|
| 조명 | 밝기 0.5~1.5배, 색온도, 방향 | 가장 효과가 큼 |
| 테이블·바닥·배경 질감/색 | 무작위 텍스처 몇 종 | |
| 카메라 위치 | **고정** (또는 ±5 mm, ±0.5° 이내) | 기존 원칙 "카메라 위치가 다른 데이터는 섞지 않음" |
| 드론·로봇·그리퍼 외형 | **고정** | 실물과 같은 물체 |
| 영상 잡음·블러 | 학습 시 증강으로 처리 | 데이터에는 깨끗한 영상 저장 |

- 첫 녹화(파이프라인 확인)는 랜덤화 없이, 그다음 켠다.
- 나중에 필요하면: 실험실을 촬영한 NuRec 배경, Cosmos 증강.

## 7. 진행 순서와 확인 방법

| 단계 | 할 일 | 확인 |
|---|---|---|
| 2-1 | 손목 카메라를 녹화용 장면에 추가, 영상 몇 장 저장 | 화면 구도가 실물 사진과 비슷한지 눈으로, 투영 오차 검사 |
| 2-2 | 녹화 스크립트, 중간 파일 저장 (에피소드 10개) | 영상·state·action 길이 일치, 성공만 저장 |
| 2-3 | LeRobot v2.1 변환기 | 기존 데이터와 같은 검사 통과, LeRobot으로 불러와 재생 |
| 2-4 | 시각 랜덤화 추가 | 영상 샘플 확인 |
| 2-5 | 본 녹화 (예: 300 에피소드, hover 섞음) | 에피소드 수, 용량, 성공률 기록 |
| 2-6 | (선택) VLA 학습 스모크 테스트 | 기존 실물 13개로 했던 π0.5 LoRA 스모크와 같은 방식 |

각 단계가 끝나면 커밋하고, 다시 해 보는 명령 가이드를 남긴다.

## 8. 검토가 필요한 점 (결정해 주세요)

1. **fps:** 4장 A(30 Hz 녹화 → 25 fps 다시 샘플링)로 갈지
2. **에피소드 수와 hover 비율:** 예) 300개, static 10% / small 30% / mid 40% / big 20%
3. **해상도:** 기존과 같이 640×480 저장 (학습 때 224×224로 줄임) — 용량이 큼. 아니면 처음부터 줄일지
4. **실패 에피소드:** 성공만 저장 (기존과 같음) / 실패도 따로 저장 (나중에 분석용)
5. **선생의 속도:** 선생은 사람 텔레옵보다 빠르게 접근함(에피소드 약 5~7 s, 실물 12~30 s). 실물 데이터와 섞을 계획이면
   이 차이를 감안해야 함
6. **depth 저장:** 손목 카메라 RGB만 / RGB + depth (카메라 1대라 거리 정보가 아쉬울 수 있음)
7. **실물 데이터와 섞을지:** 섞는다면 카메라 위치·주기·스키마를 완전히 맞춰야 하고, 섞지 않으면 조금 자유로움

## 9. 위험 요소

- 렌더링 속도: 640×480 × env 여러 개는 느리고 VRAM을 많이 씀 → env 수를 줄여서 시작 (카메라 1대라 2대일 때의 절반)
- sim 영상과 실물 영상의 차이(sim2real 시각 격차): 시각 랜덤화로 줄이지만, 실물 데이터 소량과 섞는 것이 가장 확실
- 선생이 특권 정보로만 알 수 있는 행동(예: 접촉력 보고 판단)을 VLA가 따라 하기 어려울 수 있음 → 학습 후 VLA 성공률로 확인
